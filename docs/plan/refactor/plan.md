# Wandscape 重构方案（业余版）

> 目的：给重构定调，定义侦察、修改、复核的方法，不追求重构后多完美，只求可控、快速，能维持开发。
> 问题清单：`why`；进度：`status.md`；现状摸底：648 文件 / 10.1 万行，shared/* 桥包 100+ 文件，element_mappings 1187 JSON，lang 每语言 2000+ 行。

## 一、定调

1. **北极星是维持开发速度，不是架构优美。** 每次改动的验收标准只有一句：以后的开发是不是更省力。加一个"拆除按钮"从碰 20 个文件降到 3 个，就是胜利。
2. **净减量法则。** 重构步骤必须让代码变少（行数/文件数）。只搬不动、换了名字还是同样的缠绕，叫"横移"，不算重构。
3. **风险分级，小步快跑，战果先落袋。** 顺序永远是：删（零风险）→ 改名（编译兜底）→ 合并（需人工判断）→ 重组（高风险）。先做确定性高的，把信心和显性成果先拿到手，再碰结构手术。
4. **一个 commit = 一个可编译可测的原子步，每步可回滚。** 重构允许失败，但不允许失败找不到回滚点。
5. **做到病痛消失就停，不追完美。** 合并完 5 处属性定义到 1 处真定义 + 数据驱动就收工，允许别处还留一点丑。正式阶段做完后，把"顺手清理"养成日常习惯，不再开隆重项目。
6. **禁止顺手重构。** 一个改动只做一件事：不顺手改格式、不改旁边类、不改注册 id。diff 越纯，复核越便宜，回滚越干净。
7. **重构必须能被打断。** 阶段之间随时能切回去做真实需求，代码仍然健康。这个标准过滤掉一切过度规划。

## 二、侦察

原则：只侦察下两步需要的范围，不搞全项目体检。侦察产出不是文档，是一张候选改动清单表 + status.md 追加一行。

1. **数字摸底，让数字自己说话。** 包统计、文件数、行数、JSON 计数。数字就是病灶分布图。
2. **引用计数定生死。** 用 codebase-memory 图谱查 in-degree，一锤定音：
   - `0 引用` → 死代码，直接删（`core/types/NpcAttributes` 已确认）。
   - `1 引用` → 内联进调用方，两个类一起消失。
   - `同包内 2~N 引用` → 合并收敛的对象（五处 NPC 属性定义）。
   - `跨包高引用` → 只改名字不动结构，保守处理。
3. **依赖图找搭桥点。** `shared/event`、`shared/api`、`engine/boundary` 的真实使用方；纯转发类 → Tier 3；环 → Tier 4。
4. **痛点反向侦察（苍蝇哲学）。** 每加一个功能/修一个 bug 记一笔：绕了几个包、碰几个文件。绕 10 个文件的地方就是热度最高的病灶。
5. **适配 MC 特有坑。** 代码类名被 `lang/*.json`、NBT 键、注册 id、JSON 数据引用时 grep 字符串查引用；代码删了字符串还挂着会运行期崩或存档炸。侦察阶段就标出"哪些类名出现在字符串里"。
6. **产物形态。** 候选表：`文件 | 症状 | 改动量粗估（S/M/L）| 风险档（1删/2改名/3合并/4重组）| 做不做`。做完一行划掉一行。

## 三、修改

**Tier 0 基线：** build + test 全绿、git 工作区干净再开干，保证后续每一步的失败都是真实的。

**Tier 1 删除（最高价值，最低风险，先做）：**
- 清 `0 引用` 类；清 `deprecated/` 等废 JSON；清无用 log（配合 Log 治理）。
- 专测死代码的 `@Test` 连测试一起删。
- 验收：build 绿。净减就是战果，先砍到 8 万行以下。

**Tier 2 机械改名（编译器当安全网）：**
- Mage→Npc 全仓统一。build 绿 = 成功。
- 改名连字符串一起：注册 id、lang key、NBT 键、JSON 中的类引用，grep 一处不落。
- 验收：build 绿 + grep 旧名零命中。

**Tier 3 合并定义（需人工判断）：**
- 属性五处定义收敛到一处：先写纯逻辑 + JSON 数据驱动 + 几个单测，再接各消费方。
- **等值验证**：改前改后各算一组样例对比，不靠眼睛靠数字。
- 验收：样例等值 + build + 相关测试绿。

**Tier 4 结构重组（最高风险，最后做）：**
- 拆 `core/engine/shared`，按功能域聚合。**铁的纪律：移动不改逻辑、改逻辑另开一步。**
- 每步一个 commit，在 worktree/独立分支上做，做完合回。
- 验收：build 绿 + 移动前后纯逻辑测试全绿（行为不变即成功）。

**横切三件套**（各当独立 mini 阶段，放结构稳定之后最顺）：
- **Log 治理拆两步**：危险/无用 log 的删除随 Tier 1 顺手做；系统性输出点审计（上屏/聊天只留错误+完成）放最后。
- **lang 分文件**：先切 1 个功能域做样板，验证流程顺手再铺全；顺手拆 switch-case。
- **UI 去堆**：抽 1 个公共 Screen 框架，改 2 个建筑 UI 验证可行性，做得动再铺全，做不动就停。

## 四、复核

1. **编译是头号复核刑具。** build 绿 = 基本盘，没有更便宜的全量检查。
2. **测试是守门员不是简历。** 改动的纯逻辑相关测试保持绿；测死代码的测试跟删。重构不改变行为，不因重构加新测试。
3. **三查清单（每次 commit 前，1 分钟）：**
   - `grep 旧类名` → 应零命中（改名完整）。
   - `grep 字符串 id`（注册名/NBT/lang key）→ 与代码一致（MC 特有）。
   - 改动前后行数对比 → 重构应净减；净增说明在横移，停下来问值不值。
4. **运行复核短清单：** 行为改动最多 1~2 条手测路径，能跑 `runGameTestServer` 的用 GameTest，禁止 runClient。
5. **提交复核：** `git status` 只含本步文件，不混入他人改动；提交后立即更新 status.md。**同一改动返工两次就停手重新侦察**，第三次别靠猜。
6. **两条不变式红线**（每次过线即红）：高兼容不硬编码（方块/物品走标签 JSON）；纯逻辑不 import MC 类。

## 阶段序列

| 阶段 | 内容 | 对应 Tier | 完成判定 |
|------|------|-----------|----------|
| 0/1 | 问题确认 / 约定去专业化 | — | ✅ / 进行中 |
| 2a | 死代码清理 | 1 删 | 行数砍到 ~8 万以下，build 绿 |
| 2b | 命名统一（Mage→Npc） | 2 改名 | grep 旧名零命中 |
| 2c | 属性收敛 | 3 合并 | 五处定义→一处，样例等值 |
| 2d | 包重组 | 4 重组 | 功能域包地图落地，行为不变 |
| 3/4/5 | UI / lang / Log | 横切 | 各按样板验证，做得动才铺全 |

核心一句话：**先把确定性高的减法做掉，让代码块头变小、找东西变快，再用编译器兜底做改名，最后才碰需要人脑判断的合并和结构。** 每一步都有验收、都能停。
