# 新文档写法定调 —— 从 Botania / Create / MineColonies 学到的经验

> 依据：`_refs/` 三个模范模组仓库内的**开发者文档**（游戏内 guidebook / wiki / 叙事不算）。
> 用途：给"重写 docs"这一步定格式与内容基调。先读本文，再决定删什么、留什么、怎么写。

---

## 一、三个模组的文档形态（事实）

### Botania —— 最小单元 + 行动型文档
- 每个子模块一个 `ARCHITECTURE.md`，**篇幅与该模块的"反直觉程度"成正比**：
  - `Xplat/ARCHITECTURE.md` 34 行 —— 因为它的构建方式真怪、有真陷阱（"Xplat JAR 绝不该出现在运行时 classpath"）。
  - `Forge/ARCHITECTURE.md` 3 行 —— "就是 Forge 侧事件注册/hook/mixin"，无坑，一句话完事。
  - `Fabric/ARCHITECTURE.md` 6 行 —— 同理。
- `doc/1.21-notes.md` = 版本迁移/内部改造**清单**，不是叙述文；做完的项划 `~~` 留在原地，是"活文档"不是"史书"。
- `CONTRIBUTING.md` = 按**动作**组织：报 issue / 提 PR / 维护者发版 / 写 GameTest，全是编号步骤和命令。
- 全仓只有一份 changelog（`web/changelog.md`）；CONTRIBUTING 里只引用它，不复制。

### Create —— 文档极简，只在"代码会咬人"的地方写
- 全仓零架构叙述。根级 markdown 只有 README（对外门面）、changelog.md（唯一日志）、LICENSE、SECURITY。
- 仅有两份"技术文档"是 **co-located README**（放在代码旁边，不在统一 docs 目录）：
  - `contraptions/data/README.md` —— packet 大小限制的坑（会 chunkban），首行写到：**"This information is up-to-date as of 1.20.1."**，显式挂了时效声明。
  - `foundation/recipe/trie/README.md` —— trie 查配方算法（真算法，值得写）。
- 其余知识靠可读代码 + 游戏内 Ponder + 外部 wiki 承载。

### MineColonies —— 约定进工具，不写散文
- `CONTRIBUTING.md` 59 行 = 纯流程 / checklist，甚至含 AI 披露政策。
- `documentation/` 不是文档目录，是**风格与检查器配置**：formatter XML、checkstyle 规则、sonar 抑制表、IDE 安装步骤。约定由工具强制执行，文档头不另写"代码风格"。
- 玩家相关内容在 ABOUT / 外部 wiki，不进仓库开发者文档。

## 二、提炼出的经验

1. **叙述性架构文档必然腐烂**。"某模块如何工作"的句子，代码一改就过期，且没人记得同步。三个范模没有一份在描述"模组整体怎么运作"。
2. **文档按"行动时刻"组织，不按"主题"组织**。CONTRIBUTING=发版/提 PR 时读；1.21-notes=移植时读；co-located README=动这段代码时读。不存在"通读我才能开始"的文档。
3. **篇幅只给反直觉处**。Xplat 34 行 vs Forge 3 行就是标尺：文档请求权 = "这段代码有没有让第一次摸的人猜不到、或照着直觉写会写错的坑"。
4. **约定进工具**。能靠 spotless/checkstyle/formatter/sonar 强制的，配置即文档；手写"我们约定 X"的句子是风格文档主要的腐烂源。
5. **单源不镜像**。changelog 只存在一处，别处链接引用。镜像 = 维护成本滋生地；我们旧 docs"三套镜像互相缺包"正是这个病，修法一刀切。
6. **防腐技术**：① 显式时效声明（"信息截至 X"）；② 做完的待办划 `~~` 留痕，不删不重写；③ 写明"这文档不覆盖什么"。
7. **玩家文档与开发者文档彻底分开**。guidebook（玩家）与 dev docs（开发者）是两个体系，绝不混进一个文件。

## 三、对新 docs 的定调

### 允许的文档类型（按需取用，凑不齐不丢人）

| 类型 | 内容 | 何时被读 | 范模 |
|---|---|---|---|
| CLAUDE.md | 入口 + 不可违反的铁律 + 工作流 | 每次会话 | 已有，保留，双向链接 docs |
| 域 / 模块短说明 | 每个功能域一个文件，只写反直觉之处和必踩的坑 | 第一次碰该域 | Botania `ARCHITECTURE.md` |
| 迁移 / 移植 checklist | 一个版本一节，做完划 `~~`，不删 | 升版本 / 改格式时 | Botania `doc/1.21-notes.md` |
| 数据格式 + 迁移链 | 唯一会"越攒越多"的兼容记载，按版本号组织 | 改 JSON/NBT/SavedData 时 | 数据兼容纪律 |
| 决策记录（ADR 表） | 一行一条：日期 + 决策 + 一句话为什么 | 重做该决策时 | 取代 decision.md |
| co-located README | 只放"代码会咬人"处，挨着代码放 | 摸那段代码时 | Create 两份 README |

### 内容三问（每份文档开写前先过）

1. 读者在哪个**动作**里需要我？——说不出来，不写。
2. 这段话三个月后会不会被代码推翻？——会，改成"去读 X 文件"，或删。
3. 还有没有人会在别处写同样的事？——有，留一处，别处链接。

### 硬性规则

- **不写叙述性架构文**。域内逻辑以代码为准；文档只记常识无法推断的坑与决策。
- 每份文档头部标**【何时读】【不包含什么】**——防"以为覆盖了"的假安全感。
- 时效声明：易过期内容标"信息截至 <日期/版本>"。
- 不做镜像，引用就链接。
- 删除优先：decision.md 里要翻旧账才找得到的决定，对写代码没价值，整段砍。
- 玩家侧任何内容（guidebook / wiki / 叙事）不进 docs/。

### decision.md 的处置

1. 压缩成 ADR 表：每行 日期 + 决策 + 一句话 why；**能用代码/CLAUDE.md 表达就删**。
2. 正文叙述一律删除，不保留"背景故事"。
3. 保留下来的标准 = "这句决策是代码里看不出、且未来很可能重做需要参考"（如：纯逻辑不 import MC、归属看语义不看来向、兼容走版本号、游客≠常驻市民）。
4. 删完量级参照：Botania 全仓手写 markdown 约 8-9 个文件——我们新 docs 目标接近这个量级，而非现在的三套目录。

## 四、落地顺序建议

1. 归档现有 docs：能删的先删（三套镜像、decision 正文、被 status/CLAUDE.md 取代的旧 plan）。
2. 保留下来的重写成 checklist / 短说明形态，头部分别标注【何时读】【不包含】。
3. 坑文档 co-located 到对应代码目录，而不是收进统一 docs 目录。
4. 每个功能域只留一份短说明；若该域"就是普通代码，没坑"，连这一份也不留。
